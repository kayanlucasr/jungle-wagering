## A. Resumo executivo

**Parecer: NÃO PRONTO para declarar conformidade final com o desafio.** O processador
funciona nos cenários financeiros/distribuídos executados: 277 testes passaram, a
validação com três APIs/11 papéis passou, e uma instalação nova da imagem final
também passou. Isso não sana automaticamente requisitos de conformidade ausentes.

Permanecem: **P1-02**, ponto de extensão em código exigido pela opção sem IdP; e
**P1-01**, decisão/aceite da política adicional que exclui REFUND e ROLLBACK diretos
entre si. Há ainda diferença de modelagem Inbox/Outbox e dois advisories transitivos.
Nenhum defeito P0 financeiro foi reproduzido; não houve alteração automática de
política, constraint, privilégio, dependência ou implantação principal.

A auditoria/documentação foi entregue com as pendências explícitas. O critério de
aceite de não haver P0/P1 pendente para declarar o projeto pronto **não está atendido**.

## E. Correção financeira

As suítes atuais comprovam dinheiro exato/imutável e escala/moeda inválidas recusadas;
saldo não negativo por domínio/schema; unicidade de wallet/identidades; versões;
OPENING interno, abertura positiva atômica e zero sem ledger; LOSS/rejeições sem
movimento; terminais/snapshots/ledger imutáveis; referências válidas e inválidas;
ROLLBACK de WIN/REFUND sujeito a saldo; reconciliação e diagnóstico de fixtures.

Seis pontos de falha SQL conferiram rollback de transação, inbox, wallet, ledger e
outbox; retry aplicou uma vez. Outra conexão foi terminada antes de COMMIT e a
identidade foi consultada em conexão nova antes de repetir. Resposta perdida depois
de commit real é testada separadamente por confirmação de inbox. Não se tratou uma
exceção como prova de rollback, nem se simulou partição física no exato COMMIT.

Nenhum trigger foi desativado em banco existente. Nenhum dado financeiro principal
foi alterado. Testes da política interna não são apresentados como aceite externo
da interpretação de reversões ainda pendente.

- C: wallet B confirmou enquanto lock SQL real ainda retinha A.
- D: REFUND/ROLLBACK concorrentes → uma compensação pela política atual, outra rejeitada.
- E: reversão sem saldo → REVERSAL_INSUFFICIENT_FUNDS, sem saldo negativo/ledger extra.
- Replay preservou saldo histórico após movimento posterior, resolução e reinício.

Carga pequena reproduzível: 94 HTTP + 24 envios SQS, 57 transações externas distintas,
75 respostas HTTP 200 (incluindo replays), 19 rejeições esperadas e **zero erro
operacional**. As 38 carteiras reconciliaram; 171 eventos publicados; outbox final zero.
Na execução distribuída: 44,74 operações de transporte/s; HTTP p50/p95/p99 de
553,52/696,33/771,81 ms. A repetição standalone observou 48,84 operações/s e

## G. Mensageria, recuperação e observabilidade

FIFO real confirmou grupo/dedup, long polling, visibilidade e redelivery. Inbox
persistente evitou duplicação; ACK ocorreu depois do commit. Dois publishers usaram
claims/leases/fencing. SIGKILL após envio preservou eventId; subscriber de projeção
deduplicou persistentemente eventos cujo transporte contornou dedup do SQS.

Consumer foi morto após commit antes do ACK; scheduler foi morto durante claim e
antes/depois do commit. O restart conjunto encerrou **11 containers com código 137**;
seis mensagens, seis referências pendentes e 18 eventos outbox foram preparados
durante a parada, e 12 operações foram retomadas sem dupla movimentação. As carteiras
reconciliaram e os snapshots históricos permaneceram corretos. SIGTERM foi testado
separadamente como drenagem; não foi chamado de crash.

Logs atuais: 848 registros JSON validados, 83 entregas confirmadas e 289 publicações
observadas no experimento completo. Snapshots de métricas cobrem status, duplicatas,
retries, locks, DLQ, outbox lag/depth, pendências e duração. São observações por
processo/voláteis; não substituem o ledger nem agregação persistente. Publisher
separa eventId de messageId. Nenhum exporter/serviço extra foi instalado.

## I. Limitações e preparação do envio

Além dos achados prioritários, a instalação principal continua antiga: três APIs
stage1 unhealthy, somente a migration inicial, filas/workers ausentes. Foi preservada;
o checkout e os ambientes descartáveis são as evidências de reprodução. Não se deve
demonstrar essa instalação antiga como a versão final.

Sem IdP real, double-entry, frontend, exporter agregado, SLA, HA ou durabilidade local
do broker equivalente à AWS. Workers principais não têm healthcheck HTTP; o ambiente
distribuído usa startup/heartbeat de teste e cenários funcionais. C16/C45 e a decisão
de reversões precisam ser tratados antes de anunciar conformidade completa.

Para preparar o envio:

1. Revisar/aprovar as propostas P1; não ocultar a diferença de política ao avaliador.
2. Decidir a remediação/aceitação dos avisos de dependências e da forma Inbox/Outbox.
3. Após alterações aprovadas, repetir a bateria e atualizar a matriz/parecer com a
   nova execução; não reutilizar este PASS para um novo schema ou lockfile.
4. Revisar `git status`, `git diff --check`, diffs e arquivos novos. Incluir fonte,
   migrations, lockfile, documentação e evidências selecionadas; excluir somente
   do pacote os caminhos já ignorados. Não enviar .env, node_modules, dist, .tools
   ou logs brutos. Nenhum arquivo precisa ser removido do disco para essa seleção.
5. Fornecer README e comandos abaixo. Se criar ZIP, revisar a seleção explicitamente;
   nenhum ZIP, commit ou publicação foi realizado nesta etapa.

Comandos de reprodução funcional, em checkout com Bun/Docker disponíveis:

```text
bun install --frozen-lockfile
bun run test:build
bun run test
bun run test:integration:docker
bun run test:distributed:docker --evidence-dir docs/stage-8
bun run test:load --evidence-dir docs/stage-8
bun audit --json
```

O audit retorna exit 1 enquanto os avisos permanecerem. Fluxo de aplicação em máquina
limpa: preparar `.env.example` conforme README e executar `bun run stack:scale`;
para isolamento sem tocar no principal, usar o override/comandos de
[AUDIT.md](docs/stage-8/AUDIT.md). Ele não exige dados manuais, publica nenhuma porta
e usa PostgreSQL tmpfs/banco exclusivo. Não executar upgrade no principal por engano.

Sugestão de commit **apenas para revisão**, sem criá-lo:
